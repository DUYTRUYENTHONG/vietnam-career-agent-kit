# Campaign goals and continuity

A campaign target can span several finite application batches and chat turns.
Finishing a batch is a checkpoint; it does not finish the campaign. Continue
independent authorized work while useful eligible jobs remain. A blocked vacancy
does not block discovery, assessment or preparation for other vacancies.

This is an operator workflow, not a new CLI command, scheduler or unattended
browser worker. It does not broaden platform permission, host permission or an
approved execution manifest. The core's finite limits and expiry still apply.

## Record the goal privately

When the user explicitly requests a persistent goal and the host supports it,
create or reuse that host goal. Do not create a competing active goal. Otherwise
save an operator note in the selected external private workspace and explain that
the host has no persistent goal facility. A note alone cannot schedule work.

Use this template privately; replace the placeholders with confirmed facts:

```text
Objective: Reach <target> new suitable, confirmed applications.
Candidate/workspace: <one explicitly selected private workspace>
Scope: <confirmed roles, seniority, employment types, locations, remote eligibility>
Exclusions: <prior applications, employers, duplicate requisitions, other limits>
Baseline: <ledger-derived confirmed-new count>, as of <timestamp>
Counting: Exclude prior reports, duplicates, drafts, uploads and uncertain attempts.
Execution: Use supported tools and each current exact permitted execution scope.
Evidence: Preserve attempt-before-submit records and immutable observed receipts.
Checkpoint: <private tracker path>; list unresolved facts and next viable actions.
Completion: Target reached, qualifying receipts reconciled and tracker exported.
```

Keep the candidate's goal, ledger, contacts, CVs, answers, screenshots and receipts
outside public Git. The repository's GOAL.md describes the product. Never replace
it with a personal campaign or publish a real candidate as a reusable example.

## Resume and continue

1. Reuse the selected workspace and read `resume` plus the latest private
   checkpoint. Reconcile confirmed, prior-reported and uncertain outcomes from
   the canonical ledger. Check current facts and artifacts before using them.
2. Deduplicate stable employer/requisition and source IDs before preparation and
   again before final submission. Resolve uncertain attempts read-only; never
   repeat a final attempt just because a previous chat ended.
3. Discover a finite next batch within the confirmed scope. Verify the full JD,
   live destination, eligibility and operation-specific permission. Record
   searches, exclusions and blocked leads so later passes do not repeat dead ends.
4. Prepare and review source-backed packages. Execute only within current exact
   authorization and supported host actions. Reuse valid authorization; do not
   invent approvals, extend expiry or bypass a required action-time confirmation.
5. Record each observed outcome, preserve submitted snapshots and export the
   private tracker after each pass. Report the confirmed-new count against the
   target separately from prior reports, prepared packages and unknown attempts.
6. Continue with another finite batch while independent authorized work remains.
   If one job needs an unknown answer, user challenge or unavailable tool, record
   its specific blocker and pursue other suitable jobs. Never relax fit or location
   constraints to fill a quota.

Ending an execution scope requires a new valid scope before more external writes;
the campaign goal itself grants none. Discovery and local preparation can continue
within their own permitted scope. Do not stop all work solely because a batch
contains one blocked job or reaches its submission limit.

## Checkpoint and completion

During work, give concise progress updates and a timestamped tracker table after
each pass. Before yielding, save the latest ledger-derived count, exact completed
work, remaining blockers, pending unknown outcomes and concrete next actions in
the private checkpoint. Do not claim background work will continue unless an
actual supported automation was separately requested and configured.

Mark a goal complete only when its acceptance criteria are met and no required
work remains. A response ending, a batch ending, exhausted local time or a blocked
vacancy is not completion. Follow the host's actual goal lifecycle rules for
pause, blocking and budget limits. If the user changes scope, preserve the history
and reconcile the target rather than resetting successful submissions.

The fast `tracker` command projects recorded status; it does not independently
verify employers, artifacts or approvals. Use the normal `resume`, content and
execution checks before acting. This guidance adds no schema, runtime adapter or
native-host compatibility claim.
