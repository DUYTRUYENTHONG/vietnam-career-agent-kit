# Faster discovery with supported host tools

This is instruction-only guidance reviewed 22 October 2026, not an installed
connector, permission grant or measured live throughput improvement. The local
core still imports structured JDs. No new network client or dependency is added.

## Reduce work before browser forms

1. Read the selected private checkpoint and canonical ledger once per pass.
   Reuse source coverage, stable vacancy IDs and recorded exclusions. Revisit an
   unchanged blocked lead only for new evidence or a stated recheck date.
2. Agree the role families to discover. With candidate authorization, adjacent
   implementation, business analysis, technical customer success, support and
   automation operations can broaden recall. Keep location, employment type and
   seniority limits. An adjacent title is a lead, not evidence of qualification.
3. Set a finite employer/source/query/job/time budget. Prefer a supported host's
   permitted read of a documented public board list over opening every job page.
   Record endpoint, retrieval time, employer tenant, limits and inaccessible or
   incomplete pages. Unknown source permission remains manual.
4. Normalize and deduplicate IDs before spending reasoning on full JDs. Filter
   obvious location/employment mismatches, then inspect full requirements for
   remaining leads. Remote alone does not establish country eligibility. Never
   infer years of experience from tool familiarity or overlapping jobs.
5. Import a complete verified JD and assess every requirement before tailoring.
   Prepare Strong/Plausible fits; retain gaps and exclusions. Refresh liveness,
   form questions and action permission at the actual application destination.

Small finite exact batches and one browser coordinator remain the execution
model. Use launch-execution and advance-execution to reduce local transport calls;
check-action, document review and attempt-before-submit remain required.

## Primary API references

| Provider | Documented read option | Coverage and boundary |
|---|---|---|
| [Greenhouse Job Board API](https://docs.greenhouse.io/job-board.html) | GET /v1/boards/{board_token}/jobs with content=true | Public GET endpoints need no authentication; the list can include descriptions. The application POST requires an employer API key. No application API is integrated here. |
| [Lever Postings API](https://github.com/lever/postings-api) | GET /v0/postings/{site}?mode=json with skip/limit | Published tenant jobs, paginated; custom application questions are not exposed. This is not global full-text job search. |
| [SmartRecruiters Posting API](https://developers.smartrecruiters.com/docs/endpoints) | GET /v1/companies/{companyIdentifier}/postings with limit/offset | Active tenant postings; list fields may be incomplete, so details need verification. Do not confuse it with authenticated management endpoints. |

The operator must verify current per-source and host permission, employer identity
and limits. Do not use a public read endpoint as submission authorization, invent
credentials, extract cookies, bypass challenges or substitute HTTP for a denied
browser action. Never send candidate data in a public discovery request.

No provider code, SDK, skill or examples are copied or installed. A future
connector needs bounded bytes/pages/time, redirect and URL validation, error/rate
handling, source evidence, isolated fictional tests and explicit compatibility
results before the registry may call it implemented. A bulk list can reduce
discovery reads; it cannot establish a 100/hour confirmed-application rate.
